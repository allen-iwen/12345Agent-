# 开源决策模型（laya）本地部署与实测报告

> 结论先行：**本地部署成功、零成本、CPU 可跑**；但在**中文零样本**条件下，laya 的准确率不足以替代我们现有的「规则引擎 + 生成模型」判断链。本报告给出全部实测数据与架构取舍依据。
> 生成方式：`python scripts/eval_classify_jev.py`、`python scripts/eval_laya_signals.py`（可复现）

## 一、部署可行性（本机实测）

| 项目 | 实测 |
|---|---|
| 模型 | `convaiinnovations/laya` 的 **multilingual** 检查点（mmBERT-base，322M，Apache 2.0） |
| 体积 | 647 MB（safetensors，F16） |
| 下载 | 38 秒（modelscope，国内源） |
| 加载 | 37 秒（CPU，进程内单例 + 后台预热） |
| 推理延迟 | **625–1082 ms / 次调用**（CPU，含 3–5 个问题；Ryzen 7 5800H） |
| 成本 | **$0**（自托管，权重开源） |
| 硬件约束 | 本机 RTX 3060 Laptop 6GB（已用 2.5GB）+ 内存仅剩 ~1.8GB → 选择 **CPU 推理**；GPU 需另装 CUDA 版 torch（未做） |
| 结论 | **可部署**。中文场景必须用 multilingual 检查点（根检查点仅英文，官方明示非拉丁文字会崩） |

## 二、实测结果（官方 18 条样例 + 构造标注集）

### 1) 事项分类（Choice，13 个选项）— 留一交叉验证

| 口径 | 准确率 | 平均延迟 |
|---|---|---|
| 生成模型链（我们的基线） | **100%（18/18）** | ~5–9 s/案 |
| laya 零样本（默认 token 预算） | 11.1%（2/18） | 2.4 s |
| laya 零样本（`head_max_len=512, max_len=1024`） | **22.2%（4/18）** | 2.5 s |

> 官方 README 已明确："base checkpoints are near chance on typed-decisions zero-shot… Laya is a fast base to specialise, not a zero-shot decision engine."
> 提高选项 token 预算确有提升（11.1% → 22.2%），但仍远低于可用线。

### 2) 安全隐患识别（Noul，12 条中文文本）

| 指标 | 结果 |
|---|---|
| 0.5 阈值准确率 | 58.3%（7/12） |
| 隐患组均值 / 非隐患组均值 | 0.922 / 0.699（差值仅 0.22） |
| 同集拟合最优阈值 0.75 | 83.3%（**乐观估计**，阈值在同批数据上拟合） |
| 典型错误 | 「楼下烧烤店油烟扰民」被判为安全隐患 **0.961**；「小区停水两天」0.648 |

### 3) 答复合规三维（Score + Noul，10 违规 / 10 合规）

| 维度 | 违规组均值 | 合规组均值 | 可分性 |
|---|---|---|---|
| 过度承诺（Score） | 1.489 | **1.615** | **方向反转，不可分**（序数原语最弱，官方已声明） |
| 隐私泄露（Noul） | 0.635 | 0.305 | 有信号（同集最优阈值 75%） |
| 正面回应（Noul） | 0.374 | 0.133 | 方向与预期相反，不可分 |

> 参照：**同一数据集上我们的规则引擎为「违规召回 100% / 合规误报 0%」**。

## 三、架构取舍（依据实测）

1. **生产判断仍以「规则引擎 + 生成模型」为主**：分类 100%、合规召回 100%/误报 0%、派单 94.4%，均显著优于 laya 零样本；
2. **laya 作为可选的辅助信号**：仅「隐私泄露 Noul」在中文上有可用分离度；已按 provider 方式接入（`DECISION_PROVIDER=laya`），可在不改动链路的前提下开关；
3. **不盲信模型自报置信度**：laya 输出置信度普遍偏低（分类 14/18 落入「转人工」区间），这本身是**诚实的不确定性表达**，可作为「拿不准就问人」的信号源——但不能替代判断；
4. **零样本不可用 ≠ 无用**：官方数据显示其微调检查点在同族基准上可达 0.766（超出教师上限）。**决赛阶段可考虑**用我们积累的工单数据微调（官方提供 2×T4 微调 notebook），目标是把分类与合规判断的天花板抬高，同时保留零成本离线推理优势。

## 五、附：与闭源 Jev 的关系

- 我们的接入层（`services/decision.py`）**同时支持** `laya`（本地开源）、`typesafe`（Jev 官方 API）、`vercel`（AI Gateway 路由到 `typesafe-ai/jev`）三种 provider，契约一致（Noul/Choice/Score → 校准概率 + 置信度门控）；
- 因此**拿到 TypeSafe Key 后可零改动切换**，届时可产出「Jev vs laya vs 生成模型链」三方对比；
- 当前选择 laya 的现实理由：**无需申请、无配额限制、可离线演示、成本为零**——这对复赛现场演示是实打实的优势。

## 六、追加实验：低表现的原因归属（不是 CPU）

**问题**：laya 表现差，是否因为本机用 CPU 推理？

**答**：不是。CPU 与 GPU 执行的是同一权重、同一前向计算，差异只在**延迟与数值精度**（同设备内延迟可比即可），
不可能造成 22% 与 100% 的差距。为把原因定位清楚，做了控制变量实验
（`scripts/probe_laya_language.py`，同一模型、同一设备、同一批 18 条官方样例）：

| 配置 | 准确率 | 平均延迟 |
|---|---|---|
| A 中文诉求 + **中文选项** | **16.7%**（3/18） | 2551 ms |
| B 英文诉求 + 英文选项 | 22.2%（4/18） | 543 ms |
| C 中文诉求 + **英文选项** | **44.4%**（8/18） | 571 ms |

**读法**：
1. 把**诉求**译成英文几乎无改善（16.7% → 22.2%）→ 不是"读不懂中文诉求"；
2. 把**选项**换成英文，准确率翻倍（16.7% → **44.4%**）→ 瓶颈在**选项文本的 token 预算**：
   我们的选项描述是中文长定义（已放宽到 500 字），中文切词后每选项 token 极多，
   `head_max_len` 预算被切碎，判定头无法区分选项——这正是官方「Honest Limits」中
   *"高基数 Choice 因每选项 token 不足而失准"* 的放大版；
3. 延迟差异（2551ms → 543ms）同样来自选项 token 数量，而非设备；
4. 叠加官方自述：base 检查点在 typed-decisions 零样本近随机（0.362 vs 多数类 0.461），
   且判定头由**英文决策数据**训练 → 中文政务分类属语言 + 领域双重域外。

**结论**：换 GPU 只能把延迟从 ~2.5s 降到几百毫秒，**不会改善准确率**。
若要用起来，正确路径是「短英文标签 + 映射表」或**微调**，而不是换硬件。

## 七、追加实验：与闭源 JEV 的同集对比（由团队成员执行，OpenRouter alpha 通道）

> 数据来源：`data/eval/openrouter_*_result.json`，报告见 `data/eval/REPORT_laya_vs_jev.md`（数字由脚本读取生成，未手工录入）

| 指标 | laya（本地 CPU） | JEV（OpenRouter） |
|---|---|---|
| 12 类分类准确率 | 22.2%（4/18） | **100.0%（18/18）** |
| 平均延迟 | 2546 ms | **603 ms** |
| 单案成本 | $0（自托管） | $0.00011 |
| 门控 auto / confirm / human | 1 / 2 / **15** | **16** / 2 / 0 |
| 安全隐患 Noul（12 条，0.5 阈值） | 58.3%（7/12） | **91.7%（11/12）** |
| 非隐患组均值（越低越好） | 0.699（多项误报为隐患） | **0.115** |
| 答复合规·过度承诺 违规/合规 | 1.489 / 1.615（**反向**） | 1.004 / 0.289 ✓ |
| 答复合规·隐私 违规/合规 | 0.635 / 0.305 ✓ | 0.298 / 0.024 ✓ |
| 答复合规·正面回应 违规/合规 | 反向 | 0.253 / 0.444 ✓ |

**两个关键判断（比准确率更重要）**：
1. **门控决定能否上生产**：laya 把 18 条中的 15 条判为「转人工」——接进现有合规机制后，
   它不再是分流器而是一条人工队列（83% 正常工单被推给人工）；JEV 为 16 条自动采用、0 条转人工。
2. **方向反了比没区分度更危险**：laya 给合规答复的"过度承诺"分（1.615）高于违规答复（1.489），
   照此设阈值会**拦下合规答复、放过违规答复**；JEV 三个维度方向全部正确。

**定位建议（一致结论）**：生产判断仍以**规则引擎**为主（同集召回 100% / 误报 0%）；
决策模型适合补规则覆盖不到的语义情况，并用**置信度门控**决定是否交人工。

## 八、生产安全：决策模型配额守卫

外部决策模型（JEV 走的是 key 的**不重置终身额度**）一旦归零，必须立即降级，否则每个案件都会
白白多一次失败请求。已在 `services/decision.py` 实现并验证：

- **自动降级**：HTTP 402/429/529/403 或响应体含 `quota / insufficient / rate limit / credit / balance / exceeded`
  → 进入冷却期（默认 900s，可配 `DECISION_DEGRADE_SECONDS`），期间 `ask()` 直接返回不可用，链路自然回退规则与本地路径；
- **保护性熔断**：`DECISION_MAX_CALLS` 设进程内调用上限（0=不限），评测/演示防刷爆额度；
- **可观测**：`decision.usage_stats()` 暴露调用次数、降级状态与剩余冷却时间；
- **可恢复**：`decision.reset_degrade()`（充值/换 key 后）或重启进程；
- **本地 provider 不受影响**：laya 自托管无配额，守卫分支自动跳过。

验证：`scripts/verify_decision_guard.py` 10/10 通过，其中第 5 项用**本地假端点返回 402**
端到端验证了「自动降级 → 后续调用被拦下不再发请求」。
