## 一、场景理解与核心问题（≤300字）

12345 热线的真实痛点不在"能不能答"，而在"每一单都要人来抠细节"：接线员边听边记，工单要素（时间/地点/人员/事件/诉求）靠手工整理，格式不统一；分类靠老坐席经验，新人面对 12 大类、职责交叉时容易派错部门；回复口径因人而异，质量不稳定；同类诉求重复来电，缺少提前发现的手段。核心问题即赛题所述四点：**工单整理效率低、分类依赖经验、部门匹配耗时、回复质量不一致**。

智能体应定位为"坐席的辅助副驾"：把录音快速变成忠实于原文的结构化工单，给出可解释的分类与转派建议、带政策依据的回复草稿；机器只出建议，放行权永远在人。我们还关注两个真实业务诉求：同类诉求短期聚集应触发"未诉先办"预警；效率提升应可量化（基层减负账本）。

## 二、整体解决方案（≤800字）

**一句话概括：以"五节点白盒链路 + 全程人工审核"为核心的 12345 工单辅助智能体——录音/文本进、可派发工单与回复草稿出，每一步可查、可改、可追溯。**

架构分五层（详见技术架构图）：

**（1）输入层**：录音上传、浏览器现场录音（现场无通话线路时模拟来电）、文本录入；同时预留运营商/呼叫中心标准对接层（挂机回调携带录音 URL、录音目录投递守护、SIP 预留），保证可真实接入政务热线——已用 6 分钟真实来电走回调全链路验证。

**（2）转写层**：科大讯飞听写 v2（WebSocket 流式、wpgs 动态修正）优先、本地 SenseVoice 兜底的双引擎；转写后先做**领域词典确定性纠错**（芜湖地名/部门/高频诉求词的同音近音，如"镜糊区→镜湖区""印井盖→窨井盖"），再由 LLM 做"只删噪声、事实逐字保留"的降噪整理；**原始转写全文随案留存**作为证据。

**（3）智能体链路层**（LangGraph 五节点）：诉求理解 → 标准化工单 → 事项分类 → 承办推荐 → 答复草拟，节点间产物结构化传递。分类与转派由三类知识支撑：12 大类目录（含定义/典型情形/**易混淆辨析**）、18 条官方样例工单的 BM25 相似检索 few-shot、部门职责规则库（主办/协办/识别词）。答复引用政策 RAG（8 部公开法规全文，bge-small-zh 向量检索），**引用真实性由 QC 校验，防虚构法条**。职责交叉/信息不足时显式标记 needs_human_judgment，同时仍给出参考建议。

**（4）人工审核层**：每个节点产物在坐席工作台**分节"确认/修改"**，修改可触发链路按新事实重跑；四节全审后由人工"最终放行"才归档——智能体不直接派单、不直接向群众发送任何内容。

**（5）应用层**：**白盒轨迹**（每节点输入/输出/耗时/版本存 SQLite，可回放可审计）、**未诉先办预警**（同点位+同分类 7 日内 ≥3 件聚集提示并案）、**基层减负账本**（智能体 1–2 分钟/案 vs 人工约 20 分钟工序基准）。

**实测效果**：18 条官方工单留一交叉验证，分类准确率从基线 72.2% 提升至 **100%**（目录知识富化后，边界错例全部翻正）；6 分钟真实来电 40–60 秒完成转写；全链路单案 1–2 分钟。

## 三、核心创新与应用价值（创新点 ≤3 项）

**创新 1 · 白盒可审计链路——解决政务场景"AI 黑盒不敢用"**：五个节点全部留痕（输入/输出/耗时/提示词版本），每案可回放，审核界面直接展示推理依据与置信度；职责交叉、信息不足时显式交人工判断，而不是硬给答案。

**创新 2 · 未诉先办苗头预警——从"接诉即办"到"未诉先办"**：同点位+同分类诉求 7 日内 ≥3 件自动聚集告警，列出同源案件清单，建议并案核查与主动治理，呼应国办发〔2020〕53 号深化方向。

**创新 3 · 防幻觉与证据保全设计**：政策引用 QC 校验（不在库的引用标警）、转写原始全文留存、领域词典确定性纠错（白盒替换报告）、LLM 降噪"事实逐字保留 + 过度删改自动回退"——生成结果可信可查。

**应用价值**：单案处理从约 20 分钟降到 1–2 分钟（智能体部分），分类准确可验证，减负效果有账可查；系统不改变现有"人工负责制"，可直接嵌入现有话务流程灰度试用。

## 四、技术、数据与安全可行性（≤500字）

**技术**：全栈 MVP 已实现（Python/FastAPI + LangGraph + React）。关键能力均有成熟组件且已实测：讯飞 v2 流式听写（6 分钟录音 40–60s 转写完成）+ SenseVoice 本地兜底（断网可用）；主流大模型驱动五节点（JSON 模式输出 + 结构化校验）；政策 RAG 用 bge-small-zh-v1.5（约 90MB 轻量、可离线）+ Chroma；BM25 官方样例检索。长音频分段、wpgs 修正帧合并、并发写库等风险点已在开发中实测解决。

**数据**：以主办方 18 条官方样例工单为 few-shot 与评测底料（留一交叉验证防泄漏，防"答案混进参考"）；12 大类目录按赛题口径建设并补充辨析知识；政策库 8 部法规均为公开发布文件、注明名称与来源；部门职责规则参照政府公开职责目录整理。

**安全合规**：①密钥仅存本地 .env，不入 Git、不入提交包（打包前已做密钥扫描）；②官方样例已脱敏（"某先生"式称呼、无完整联系方式），作品不含真实个人敏感信息；③防幻觉三道闸：政策引用 QC 校验、转写原文留存、降噪保守策略；④全程人工审核：分节确认 + 最终放行，系统不自动派单、不自动向群众发送内容；⑤运营商对接层预留回调鉴权（X-Telephony-Secret）。

## 六、核心闭环说明（诉求输入 → 关键信息提取 → 标准化工单 → 事项分类与转派建议 → 人工确认）

智能体按一条可回溯的流水线运转：坐席录入录音或文本后，系统先转写降噪，再依次产出 ①要素清单（时间/地点/人员/事件/诉求，缺项提示补充）→ ②标准化工单（标题/摘要/诉求/关键要素）→ ③事项类别（12 选 1 + 候选得分 + 理由）→ ④承办单位（主办/协办 + 依据）。四项产物全部进入人工审核门：坐席逐节"确认"或"修改"（修改可触发链路按新事实重跑），全部通过后"最终放行"归档；归档案件进入历史库，反哺后续案件的相似检索。信息不足或职责交叉时，系统不擅自定论，而是标记"需人工判断"并附参考建议——闭环每一环的产物都能在工作台查到原始依据。详见 `03_业务流程图.png`。

## 七、示例：原始输入 → 结构化工单及转派建议（系统真实输出节选）

**原始输入**（文本录入 / 语音转写均可）：

> 我是万春花园小区的住户，小区北门外的兄弟烧烤店每天晚上占道摆桌，油烟直接飘进家里，一直到凌晨两点多特别吵，跟物业反映过没人管。请相关部门尽快处理。

**系统输出**：

| 字段 | 内容 |
|---|---|
| 工单标题 | 关于万春花园小区北门兄弟烧烤店占道经营及油烟噪音扰民的问题 |
| 建议事项类别 | 城市管理（候选：城市管理 0.62 / 生态环境 0.28 / 市场监管 0.10） |
| 关键要素 | 地点=万春花园北门；对象=兄弟烧烤店；时间=每日夜间至凌晨两点；事件=占道摆桌 + 油烟 + 噪音；诉求=依法整治 |
| 承办单位（建议） | **主办**：城市管理局（占道经营、市容职责）；**协办**：生态环境分局（油烟）、市场监督管理局（经营资质） |
| 转派提示 | ⚠ 职责交叉（城管+环保），建议人工确认主办单位 |
| 预回复（节选） | "您好，您反映的烧烤店占道经营及油烟噪音扰民问题已受理，已转城市管理局会同相关部门核实处理，办理结果将及时向您反馈。" |
| 相似历史工单 | 系统同步给出同类官方样例工单供坐席参照 |

## 八、哪些结果可以自动生成，哪些必须人工审核

**可自动生成（仅供参考）**：转写文本与降噪整理稿、要素清单、标准化工单全文、事项类别与候选得分、主办/协办单位建议、预回复与回访话术、相似案例推荐、质量检查结果、未诉先办预警提示。

**必须人工审核**：工单内容的确认与修改、最终类别与派单决定（职责交叉/信息不足时系统显式提示）、预回复发送前定稿、回访话术采用、预警后的并案决策。系统硬约束：未经人工"最终放行"不得归档；任何内容不自动向群众发送。
