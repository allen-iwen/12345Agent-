# laya（本地开源）vs JEV（OpenRouter alpha）同集对比报告

- 评测日期：2026-09-21
- 数据来源：`data/eval/*.json`（本报告全部数字由 `scripts/compare_laya_vs_jev.py` 从这些文件读取后计算，未手工录入）
- laya：`convaiinnovations/laya-multilingual`，本地 CPU 推理，自托管 $0
- JEV：`typesafe/jev-1.13-20260917`（别名 `~typesafe/jev-latest`），经 OpenRouter `POST /api/alpha/decisions`

复现命令（backend 目录，key 未写入 `.env`，用环境变量覆盖）：

```bash

export DECISION_API_KEY=<your openrouter key>

venv/Scripts/python.exe -u scripts/eval_classify_jev.py
venv/Scripts/python.exe -u scripts/eval_laya_signals.py

```

## 一、事项分类（12 类中文 Choice，18 条官方样例，留一验证）

| 指标 | laya（本地） | JEV（OpenRouter） |
|---|---|---|
| **准确率** | **22.2%（4/18）** | **100.0%（18/18）** |
| 平均延迟 | 2546 ms | **603 ms** |
| 输入 token | 0（未计） | 47126 |
| 总成本（18 条） | $0 | $0.001979 |
| 单案成本 | $0（自托管） | **$0.00011** |
| 门控 auto（自动采用） | 1 | **16** |
| 门控 confirm（人工确认） | 2 | 2 |
| 门控 human（转人工） | **15** | **0** |

12 类随机猜测约 8.3%，laya 的 22.2% 基本等于"总在同一小撮类别里猜"。

**比准确率更值得看的是门控分布**：laya 把 18 条中的 15 条判为"转人工"、只有 1 条敢自动采用——在生产链路上这不是分类器，而是一条人工队列；JEV 16 条自动采用、2 条人工确认、0 条转人工。项目原本设计的"拿不准就交人工"合规机制，在 laya 上会把绝大多数正常工单都推给人工，等于没起到分流作用。

JEV 与项目里生成模型基线（提示词链 + LLM，LOO 100%）**准确率相同**，但平均延迟从"约 5–9s/案"降到 0.6s，且不需要把 12 类辨析目录塞进提示词。

## 三、答复合规三维（10 违规 / 10 合规）

| 维度 | laya 违规/合规均值 | 间隔 | JEV 违规/合规均值 | 间隔 |
|---|---|---|---|---|
| 过度承诺 score（高=违规） | 1.489 / 1.615 | **−0.126（方向反了）** | 1.004 / 0.289 | **+0.715 ✓** |
| 隐私泄露 noul（高=违规） | 0.635 / 0.305 | +0.329 ✓ | 0.298 / 0.024 | +0.274 ✓ |
| 正面回应 noul（低=违规） | 0.374 / 0.133 | +0.241（方向反了） | 0.253 / 0.444 | **−0.191 ✓** |

JEV 分维度同集最优阈值表现：

| 维度 | 阈值 | 准确率 |
|---|---|---|
| 过度承诺 Score | 1.93 | 75.0% |
| 隐私泄露 Noul | 0.88 | 65.0% |
| 正面回应 Noul | 0.20 | 75.0% |

**三个维度的方向性 JEV 全部正确，laya 有两个是反向的**：

- **过度承诺**：laya 给"合规答复"的过度承诺分（1.615）比"违规答复"（1.489）还高。这不只是"无区分度"，而是**反向相关**——照这个分数设阈值，会把合规答复拦下来、放违规答复过去。
- **正面回应**：违规组（0.374）反而高于合规组（0.133），同样反向。

隐私泄露是 laya 唯一方向正确的维度（0.635 / 0.305），但分离度也不如 JEV 干净（JEV 违规 0.298 vs 合规 0.024，合规组几乎为 0）。

注意：以上最优阈值都是**在同一批数据上拟合**的（脚本里已标注"乐观估计"），真实泛化表现需要另开测试集验证。

## 四、延迟与成本

| 场景 | laya（本地 CPU） | JEV（云 API） |
|---|---|---|
| 分类（18 条） | 2546 ms/次 | **603 ms/次** |
| 信号（32 次） | 1076 ms/次 | **576 ms/次** |

JEV 作为一次云调用反而更快——因为 laya 是本地 CPU 逐 token 前向，且首次加载还需 30–40s 预热；JEV 单次请求只做一次前向。

成本推算（JEV 单案约 $0.00011）：

| 日工单量 | JEV 日成本 | JEV 月成本 |
|---|---|---|
| 1,000 | ≈ $0.11 | ≈ $3.3 |
| 10,000 | ≈ $1.10 | ≈ $33 |
| 100,000 | ≈ $11.0 | ≈ $330 |

若按 `decision_case.assess()` 一次问 10 个问题的全案链路计，单案成本量级仍在 1e-4 美元。

## 五、结论与建议

1. **分类判断：JEV 可直接上位，laya 不可用。** 22.2% vs 100%，且 laya 的门控把 83% 工单推给人工，失去分流意义。
2. **安全门控：JEV 可用，laya 建议弃用。** 两者漏报都是 0，但 laya 误报 5/6，非隐患组均值 0.699 导致阈值无处可落。
3. **合规审查：JEV 可用（需定阈值），laya 有害。** laya 在"过度承诺"和"正面回应"两个维度上方向反了，接入会制造错误拦截。
4. **生产建议仍以规则引擎为主**：脚本自身的结论是规则引擎在同一合规集上召回 100% / 误报 0%。JEV 的合理定位是**补充**规则覆盖不到的语义情况（如口语化表达、隐式隐患），以及用置信度门控决定"是否交人工"。
5. **成本可忽略，但需加欠费守卫**：$0.00011/案 相对于 LLM 链路极低，然而 JEV 走的是 key 的 spend limit（不重置的终身额度）。接入时应挂 `budget_guard()`，额度归零时降级到规则/本地路径。

### 样本量限制（必须声明）

- 分类 18 条、隐患 12 条、合规 20 条，都是项目自有 fixture，**不是公开留出测试集**。
- 合规三维的"最优阈值"是同集拟合，属乐观估计。
- 结论方向明确（22% vs 100% 这种差距远超小样本噪声），但**具体阈值必须另开测试集重新标定**后才能上生产。
